How to Debug Data Science Projects: A Step-by-Step Python Workflow Guide

Find the source of a broken result systematically—from raw data and transformations to features, evaluation and reproducibility.

Data science projects rarely fail because of one dramatic mistake. More often, a small issue travels through a workflow: a column is parsed incorrectly, a filter removes unexpected rows, a merge duplicates records, or a feature is calculated with the wrong assumptions. By the time a model score looks strange, the original cause may be several steps upstream.

A reliable debugging process helps you isolate the earliest point where results stop matching expectations. Rather than changing several lines until the notebook runs, treat every step as a testable transformation with inputs, outputs and clear assumptions.

Core rule: reproduce the issue, narrow it to one stage, inspect evidence, make one change, and rerun the relevant checks. Keep a known-good copy of the data or output when it is safe and permitted.

1. Reproduce the problem before changing code

Start by recording what you expected, what actually happened, the code cell or script involved, and whether the issue appears every time. Capture the smallest input that reproduces the problem, removing personal or confidential information first. Avoid making several speculative fixes at once; otherwise, you may hide the original cause.

For a suspicious dataframe, inspect its shape, column names, data types and a few representative rows:

print("Shape:", df.shape)
print("Columns:", df.columns.tolist())
print(df.dtypes)
print(df.head(5))
print(df.sample(min(5, len(df)), random_state=7))

Sampling with a fixed random seed makes inspection repeatable. If the dataframe is empty, check its shape before sampling. The goal is to establish whether the data entering the stage is what you thought it was.

2. Trace data changes one step at a time

Long notebook cells make it difficult to see which operation changed the result. Split complicated transformations into named steps and record row counts at important boundaries. If a dataset unexpectedly shrinks from 50,000 rows to 800, inspect the filtering and join steps between those counts.

def report_frame(name, frame):
    print(f"{name}: rows={len(frame):,}, columns={frame.shape[1]}")
    print("Duplicate rows:", frame.duplicated().sum())
    print("Missing cells:", int(frame.isna().sum().sum()))

report_frame("raw", raw_df)
clean_df = raw_df.dropna(subset=["customer_id"])
report_frame("after customer_id filter", clean_df)

Counts are clues, not proof that a step is correct. A row reduction may be intended, but it should be explained by a clear rule. Add checks for expected ranges or uniqueness where those properties matter.

3. Debug common Pandas problems

Many data science bugs are data-shape or data-type mismatches rather than complex algorithm failures. Common examples include strings where numbers were expected, inconsistent date parsing, unexpected nulls, duplicate join keys and column names that changed after a merge.

SymptomWhat to inspectUseful next step
Arithmetic fails or sorts strangelyColumn dtype and sample valuesParse values explicitly and count conversion failures
Row count suddenly increases after a mergeUniqueness of join keys on both sidesUse merge validation such as one-to-one or many-to-one when appropriate
Expected records disappearNulls, filters, whitespace and key formattingCompare unmatched keys and inspect each filter condition
Dates are out of orderString parsing, timezone and day/month conventionsConvert to datetime with an explicit format where possible
Unexpected missing values appearFailed casts, joins and source-field completenessMeasure missingness before and after each operation

For example, use merge validation to catch a join that violates your assumption about unique customer IDs:

merged = orders.merge(
    customers,
    on="customer_id",
    how="left",
    validate="many_to_one",
    indicator=True
)
print(merged["_merge"].value_counts())

If the right-hand table contains duplicate customer IDs, a many-to-one validation can raise an error rather than silently multiplying order rows. Investigate the duplicates and decide what the correct business rule should be; do not drop them blindly.

4. Turn assumptions into assertions

An assertion can make an implicit expectation explicit. For example, if every transaction should have a non-negative amount and a unique transaction ID, check those conditions close to where the data enters your workflow.

assert "transaction_id" in df.columns
assert df["transaction_id"].notna().all()
assert df["transaction_id"].is_unique
assert (df["amount"] >= 0).all()

These checks should reflect the real dataset contract. If nulls or repeated IDs are valid for your use case, define a more suitable condition. For production code, consider descriptive exceptions or a validation library so users can understand which rule failed and why.

5. Debug feature engineering with small examples

Feature engineering can produce plausible values that are still wrong. Typical mistakes include calculating a customer’s future total using information unavailable at prediction time, grouping by the wrong key, using an incorrect time window, or accidentally including the target in the feature set.

Test transformation logic on a tiny, hand-checked example before running it across the full dataset. For a grouped total, manually calculate two or three expected values and compare them with the code output. For time-based features, verify ordering and make sure the current or future outcome has not leaked into a past prediction.

df = df.sort_values(["customer_id", "event_time"])
df["previous_amount"] = (
    df.groupby("customer_id")["amount"].shift(1)
)
# First event per customer should have no previous amount.
first_rows = df.groupby("customer_id").head(1)
assert first_rows["previous_amount"].isna().all()

This is only an example of a lag feature. In a real project, ensure timestamps are parsed consistently and rows are sorted using the actual event-time definition. Debugging should verify the intended meaning of a feature, not merely that the code executes.

6. Isolate machine learning pipeline errors

If data preparation appears correct but model behaviour is unexpected, check the boundary between features, labels, preprocessing and evaluation. Confirm that X and y have matching row counts and aligned indices, that the target is excluded from the feature matrix, and that preprocessing is fitted only on training data.

assert len(X_train) == len(y_train)
assert len(X_valid) == len(y_valid)
assert target_column not in X_train.columns

print("Train features:", X_train.shape)
print("Validation features:", X_valid.shape)
print("Train target distribution:")
print(y_train.value_counts(normalize=True, dropna=False))

Compare against a simple baseline and inspect individual errors, not only one headline metric. For classification, examine confusion matrices and precision/recall where relevant. For regression, inspect residuals and segment-level errors. A surprising metric can be caused by a label alignment bug, a split mistake, class imbalance or a mismatch between the metric and the actual goal.

When using a preprocessing pipeline, fit it on the training split and apply the fitted transformations to validation or test data. This reduces leakage risk and keeps transformation logic consistent.

7. Use logging and tests instead of relying on notebook memory

Notebooks are useful for exploration, but critical logic becomes easier to maintain when it is moved into small functions with clear inputs and outputs. Add unit tests for deterministic transformations and integration tests for the end-to-end data flow. Use logs to record row counts, schema versions and validation failures without dumping sensitive records.

  • Unit test: Does a cleaning or feature function behave correctly on a small known input?
  • Data test: Are required columns present, keys valid and values within expected ranges?
  • Integration test: Does the complete pipeline produce the expected schema and output shape?
  • Regression test: Does a previously fixed bug stay fixed after code changes?

Keep test fixtures small and readable. A test should communicate the expected behaviour to the next person who maintains the project.

8. Keep a debugging log for reproducibility

When an issue is resolved, record the symptom, root cause, evidence, change made and test added. Also capture relevant package versions, random seeds, data snapshot identifiers and configuration. Reproducibility is difficult if the source data or environment changes between the original failure and the attempted fix.

Use version control to track code changes and avoid overwriting the only copy of an important result. Do not commit secrets, personal data or restricted datasets to a public repository. Document how permitted data can be obtained and how a reader can run the project safely.

9. A practical project-debugging checklist

  • ☐ I can reproduce the problem with a clear input and expected result.
  • ☐ I checked dataframe shape, columns, types and missing values.
  • ☐ I measured row counts before and after filters and joins.
  • ☐ I validated assumptions about unique keys, ranges and categories.
  • ☐ I tested feature calculations on small, hand-checked examples.
  • ☐ I verified feature/target alignment and leakage-safe evaluation.
  • ☐ I compared individual errors and suitable baseline metrics.
  • ☐ I added a test or validation rule to catch the issue in future.
  • ☐ I documented the fix and kept sensitive data out of public files.

10. Practise debugging as part of your learning

For a portfolio exercise, take a small public dataset and deliberately introduce a few controlled problems: convert a numeric column to text, duplicate a join key, introduce missing values, shuffle labels or calculate a feature using the wrong grouping key. Write one test or check for each issue, then document the symptom, diagnosis and fix. This demonstrates analytical thinking more clearly than a notebook that only shows a final score.

Conclusion

Effective debugging is a repeatable method: reproduce the issue, inspect each transformation, turn assumptions into checks, isolate pipeline stages and add a regression test after the fix. These habits make data science projects easier to trust, explain and maintain—and they help you spend less time guessing when a result looks wrong.
