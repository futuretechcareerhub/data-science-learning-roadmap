SQL Window Functions for Data Science: 10 Practical Examples

Use window functions to compare rows, rank results, analyse changes over time and build useful business features without collapsing detail into one row per group.

Published: October 21, 2026 · Includes query patterns and practical examples

SQL window functions are valuable in data science because they calculate across related rows while keeping each row visible. Unlike a standard aggregate query that often returns one row per group, a window function can add a group-level statistic, rank or previous-row value to every record in the result.

Example setup: imagine an orders table with customer_id, order_id, order_date and amount. The examples use broadly supported SQL syntax, though date arithmetic and a few details vary by database engine.

Window function anatomy

function_name(expression) OVER (
  PARTITION BY group_column
  ORDER BY sort_column
  ROWS BETWEEN ... AND ...
)
  • PARTITION BY divides rows into groups without combining them.
  • ORDER BY defines sequence inside each group.
  • Frame clause specifies which nearby rows an aggregate window should include.

For repeatable results, use a deterministic ordering. If dates can tie, add a unique key such as order_id as a secondary sort column.

1. Number each customer's orders with ROW_NUMBER

Use this when you need a unique sequence for each customer—for example, to identify the first order or select one record per group.

SELECT customer_id, order_id, order_date, amount,
       ROW_NUMBER() OVER (
         PARTITION BY customer_id
         ORDER BY order_date, order_id
       ) AS order_number
FROM orders;

The sequence restarts at 1 for every customer. Unlike RANK(), ROW_NUMBER() assigns a distinct number to every row, including ties.

2. Rank top performers with RANK and DENSE_RANK

SELECT customer_id, SUM(amount) AS total_spend,
       RANK() OVER (ORDER BY SUM(amount) DESC) AS spend_rank,
       DENSE_RANK() OVER (ORDER BY SUM(amount) DESC) AS dense_spend_rank
FROM orders
GROUP BY customer_id;

RANK() leaves gaps after tied positions; DENSE_RANK() does not. Use ranking functions for leaderboards, top products and customer segmentation. If you need exactly three rows, ranking ties may return more than three—choose a deterministic ROW_NUMBER() strategy instead.

3. Compare a row with the previous value using LAG

LAG() retrieves a value from an earlier row in the ordered partition. It is useful for repeat purchases, daily metrics and sequential observations.

SELECT customer_id, order_date, amount,
       LAG(amount) OVER (
         PARTITION BY customer_id
         ORDER BY order_date, order_id
       ) AS previous_order_amount
FROM orders;

The first row for each customer has no previous order, so its result is typically NULL. Decide explicitly how your analysis should treat that missing comparison.

4. Compare with the next observation using LEAD

SELECT customer_id, order_date, amount,
       LEAD(order_date) OVER (
         PARTITION BY customer_id
         ORDER BY order_date, order_id
       ) AS next_order_date
FROM orders;

LEAD() is useful for measuring time between events, identifying the next status or examining what happened after a customer interaction. The last row in each partition normally returns NULL.

5. Calculate a running total

SELECT order_date, order_id, amount,
       SUM(amount) OVER (
         ORDER BY order_date, order_id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_revenue
FROM orders;

The running total accumulates revenue in a defined sequence. The explicit ROWS frame makes row-by-row intent clear. Without a unique ordering, ties may make the sequence ambiguous.

6. Create a moving average

SELECT order_date, amount,
       AVG(amount) OVER (
         ORDER BY order_date, order_id
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
       ) AS moving_avg_7_rows
FROM orders;

This calculates an average across the current row and up to six preceding rows. It is a seven-row average, not necessarily a seven-calendar-day average. For daily analytics, aggregate to one row per date first or use a date-based range supported by your database.

7. Measure each order's share of customer spend

SELECT customer_id, order_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id) AS customer_total,
       1.0 * amount / NULLIF(
         SUM(amount) OVER (PARTITION BY customer_id), 0
       ) AS share_of_customer_spend
FROM orders;

This adds the customer's total spend and each order's proportion to every order row. NULLIF avoids division by zero; the 1.0 helps encourage decimal division in engines where integer division is a concern.

8. Find each customer's first order

WITH numbered AS (
  SELECT customer_id, order_id, order_date, amount,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY order_date, order_id
         ) AS rn
  FROM orders
)
SELECT customer_id, order_id, order_date, amount
FROM numbered
WHERE rn = 1;

Window functions generally cannot be filtered in the same query's WHERE clause because the window result is calculated later in query processing. A CTE or subquery makes the result filterable. Some modern engines also offer QUALIFY.

9. Calculate change from the previous order

WITH compared AS (
  SELECT customer_id, order_date, order_id, amount,
         LAG(amount) OVER (
           PARTITION BY customer_id
           ORDER BY order_date, order_id
         ) AS previous_amount
  FROM orders
)
SELECT customer_id, order_date, amount, previous_amount,
       amount - previous_amount AS absolute_change,
       (amount - previous_amount) / NULLIF(previous_amount, 0.0)
         AS fractional_change
FROM compared;

This pattern supports behavioural analysis and feature creation. Treat a zero previous value separately if you need to express percentage change, and confirm that the ordering reflects the business event sequence.

10. Compare a product or region with its group average

Suppose an aggregated dataset contains one row per product and region. A window average can compare each product with its region's average while preserving product-level detail.

WITH product_sales AS (
  SELECT region, product_id, SUM(amount) AS sales
  FROM orders
  GROUP BY region, product_id
)
SELECT region, product_id, sales,
       AVG(sales) OVER (PARTITION BY region) AS region_avg_sales,
       sales - AVG(sales) OVER (PARTITION BY region) AS vs_region_average
FROM product_sales;

This is useful for relative performance features and exploratory analysis. Note that the average here weights each product row equally; it is not an average across orders or customers.

Common mistakes to avoid

  • Missing or ambiguous ordering: ranking and lag results may change when ties are not resolved.
  • Confusing rows with time: seven preceding rows do not always mean seven days.
  • Filtering too early: filtering rows before the window runs can change the window's context.
  • Mixing grains: confirm whether each row represents an order, customer, day or product before interpreting a metric.
  • Ignoring NULL and zero values: decide how missing prior observations and zero denominators should be handled.
  • Assuming all SQL engines are identical: check your database's supported functions, frame syntax and date operations.

How data scientists use window functions

Window functions help create recency and frequency features, customer purchase sequences, month-over-month comparisons, product rankings and rolling statistics. They can reduce complicated self-joins and make analytical logic easier to review. They do not automatically prevent data leakage: when preparing model features, make sure each value uses only information available at prediction time.

Practice checklist

  • Write a query that numbers orders per customer.
  • Return the top three products per region, deciding how ties should work.
  • Calculate each customer's change from the previous order.
  • Compare a running total with a grouped total to validate the result.
  • Test the query on duplicate timestamps, missing values and zero amounts.
  • Document the output grain and the database engine used.

Conclusion

SQL window functions make row-level analysis more expressive: rank records, inspect sequences, calculate cumulative measures and compare observations with group statistics without losing detail. Learn the partition, ordering and frame rules first, then practise on questions where the result can be checked independently.
