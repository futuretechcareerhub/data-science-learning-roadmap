Feature Engineering for Customer Churn: Practical Data Science Examples

Build meaningful customer behaviour features, test them carefully, and keep every input valid for the prediction timeline.

Published: November 28, 2026

A customer churn dataset might contain a customer ID, subscription plan, monthly bill, support tickets and login activity. These raw columns provide a starting point, but they may not describe the behaviour that signals a customer is becoming disengaged. Feature engineering turns available data into meaningful measurements that help a model identify patterns—while keeping the information valid for the moment a prediction is made.

This walkthrough focuses on a practical customer churn scenario. Instead of repeating a general list of preprocessing techniques, it shows how to create and evaluate behaviour-based features from a business question.

1. Define the Prediction Moment Before Creating Features

Suppose a subscription business wants to identify customers likely to cancel within the next 30 days. Define a cutoff date for each customer observation. Inputs must come from information recorded on or before that cutoff, and the label should represent cancellation during the following 30-day window.

  • Prediction unit: one customer at one cutoff date.
  • Target: cancellation within the next 30 days.
  • Feature window: behaviour observed in the 30, 60 or 90 days before cutoff.
  • Business use: prioritize outreach or service interventions.

These definitions prevent future information from accidentally entering the model.

3. Build Features with Pandas

Imagine a usage table with customer ID and activity date. A simple summary can count recent sessions and calculate recency for a single cutoff. This example assumes that the source table contains only activity events and that the cutoff is set for the prediction snapshot.

import pandas as pd

cutoff = pd.Timestamp("2026-10-31")
usage = pd.read_csv("customer_usage.csv", parse_dates=["activity_date"])

# Keep events that would be known at the prediction cutoff
past_usage = usage.loc[usage["activity_date"] <= cutoff].copy()

recent = past_usage.loc[
    past_usage["activity_date"] > cutoff - pd.Timedelta(days=30)
]

last_activity = past_usage.groupby("customer_id")["activity_date"].max()
sessions_30d = recent.groupby("customer_id").size()

features = pd.DataFrame({
    "days_since_last_activity": (cutoff - last_activity).dt.days,
    "sessions_last_30d": sessions_30d
}).fillna({"sessions_last_30d": 0})

features["sessions_last_30d"] = features["sessions_last_30d"].astype(int)
print(features.head())

For a real churn dataset, build a row for every customer in the snapshot—even those with no recent activity—then join the feature summaries to that customer list. Missing recency should be represented thoughtfully (for example, a never-active flag plus an appropriate missing-value rule), rather than silently treating every missing value as identical.

4. Add Change and Trend Features

A single activity count may miss whether engagement is falling. Compare two windows of equal length to make a trend feature. The following pattern illustrates a recent-versus-prior 30-day count:

recent_30 = past_usage.loc[
    past_usage["activity_date"] > cutoff - pd.Timedelta(days=30)
].groupby("customer_id").size()

prior_30 = past_usage.loc[
    (past_usage["activity_date"] > cutoff - pd.Timedelta(days=60)) &
    (past_usage["activity_date"] <= cutoff - pd.Timedelta(days=30))
].groupby("customer_id").size()

trend = pd.concat([recent_30, prior_30], axis=1).fillna(0)
trend.columns = ["recent_sessions", "prior_sessions"]
trend["session_change"] = trend["recent_sessions"] - trend["prior_sessions"]
trend["recent_to_prior_ratio"] = (
    trend["recent_sessions"] / trend["prior_sessions"].clip(lower=1)
)

Use the change and ratio together only if they make sense for the model and remain stable. Ratios can be extreme when the prior count is very small; consider a capped, log-transformed or alternative difference feature after inspecting distributions.

5. Treat Categories and Numeric Features Carefully

  • Standardize category labels such as plan names and payment methods before encoding.
  • One-hot encoding is a transparent baseline for modest category counts.
  • Use an explicit unknown-category strategy for categories appearing after training.
  • Scale numeric columns when the algorithm is sensitive to feature magnitude, such as distance-based methods or many linear models.
  • Impute missing values using training data only, and consider adding a missingness indicator when the absence itself carries information.

Build transformations in a scikit-learn pipeline so fitting and applying preprocessing remain consistent. For time-based prediction, use a chronological validation strategy instead of a random split when it better represents the future use case.

6. Compare Feature Groups with a Baseline

Do not assume that more features automatically improve predictions. Start with a simple baseline, then add groups such as engagement, billing, support and subscription-change features. Track validation metrics, calibration, complexity and stability over multiple time periods.

ExperimentQuestion to ask
BaselineHow well does a model perform using a small set of clean features?
Engagement featuresDo recency, counts and activity trends improve validation?
Billing featuresDo payment issues or bill changes add useful signal?
Support featuresAre tickets informative beyond activity and plan information?
Combined featuresDoes the added complexity create stable, useful gains?

Choose metrics based on the intervention. If the retention team can contact only a limited number of customers, precision among the top-ranked customers or lift in the top segment may be more actionable than overall accuracy. Monitor recall and false positives as well, because missing at-risk customers and contacting healthy customers both have costs.

7. Feature Engineering Mistakes to Avoid

  • Using future events: cancellations, tickets or usage after the cutoff cannot be features for that prediction.
  • Leaking label construction: do not include columns that directly reveal the next-30-day cancellation outcome.
  • Overlapping windows: define inclusive/exclusive boundaries and test them so events are not double-counted.
  • Customer duplication: ensure the snapshot has the intended one-row-per-customer prediction unit.
  • Ignoring data availability: a feature is not valid if it is delayed or unavailable when predictions are generated.
  • Unverified improvement: feature importance does not prove causality or guarantee that an intervention will reduce churn.

8. A Reusable Feature Review Checklist

  • Target, prediction unit and cutoff date are written down.
  • Every feature has a definition, source and time window.
  • Feature values are available at prediction time.
  • Missingness, outliers, units and category values have been reviewed.
  • Transformations are fit only on training data.
  • Validation reflects the expected future deployment setting.
  • Feature groups are tested against a baseline with relevant metrics.
  • Features and transformations are documented for repeatable inference.

Conclusion

Feature engineering is a disciplined way to represent business behaviour in model-ready data. For churn prediction, activity recency, usage trends, support history and billing changes can be useful candidates—but only when their definitions match the prediction timeline and their contribution is validated. Build a clear baseline, test features in groups, document assumptions and keep the pipeline reproducible.
