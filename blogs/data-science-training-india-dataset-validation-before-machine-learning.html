How Data Science Training in India Helps You Learn Dataset Validation Before Machine Learning

Build the habit of checking data quality before trusting a chart, training a model, or sharing a result.

Published: October 24, 2026 · Reading time: 8–10 minutes

Machine learning begins long before you call fit(). A dataset can load without errors and still contain duplicated records, inconsistent categories, impossible values, or missing information that changes the conclusion. Learning to spot these problems is a core practical skill for anyone exploring Data Science Training in India and building projects with Python.

This guide walks through a repeatable dataset-validation routine you can apply to a class assignment, a portfolio project, or a business dataset. The goal is not to make data look perfect at any cost. It is to understand what is wrong, decide what matters for the question, and document the decision.

Key principle: Validate against the meaning and intended use of the data. A missing value is not always an error, and an unusual value is not automatically an outlier to delete.

1. Start with the question and the unit of observation

Before checking columns, write down what one row represents: a customer, an order, a day, a device reading, or something else. Then define the target question and the expected time period. These details determine which duplicates, ranges, and missing values are genuinely suspicious.

  • Unit: What does one row represent?
  • Key: Which field or combination should uniquely identify a record?
  • Target: What outcome will the model predict, if there is one?
  • Timing: When was each feature available relative to the prediction?

For example, two rows for the same customer may be valid if each row is a separate order. They are duplicates only if the business definition says that the order identifier should be unique.

2. Inspect shape, column types and sample values

Use a quick first pass to understand the dataset before changing it.

import pandas as pd

df = pd.read_csv("customer_data.csv")

print("Rows and columns:", df.shape)
print(df.head())
print(df.info())
print(df.describe(include="all").T)

Check whether numeric-looking fields were imported as text, dates are parsed consistently, and categorical columns contain unexpected spellings such as "Delhi", "delhi", and "DELHI". Do not convert a column blindly: a postal code may look numeric but should usually be treated as an identifier rather than a quantity.

3. Measure missing values before choosing a treatment

Missing data can arise from optional fields, system failures, or a process that only records certain events. Measure both the count and percentage, then decide whether to retain, impute, flag, or exclude a field based on the problem.

missing = pd.DataFrame({
    "missing_count": df.isna().sum(),
    "missing_percent": (df.isna().mean() * 100).round(2)
}).sort_values("missing_percent", ascending=False)

print(missing[missing["missing_count"] > 0])

For a small amount of missing information, a suitable imputation strategy may be enough. For a column that is mostly empty, ask whether it is necessary and whether its absence itself carries meaning. Fit imputers on training data only; calculating imputation values from the full dataset before splitting can leak information into validation or test results.

4. Check duplicate rows and key uniqueness

# Exact duplicate rows
print("Exact duplicate rows:", df.duplicated().sum())

# Example: order_id is expected to be unique
if "order_id" in df.columns:
    print("Repeated order IDs:", df["order_id"].duplicated().sum())

Inspect examples before removing anything. Exact duplicate rows may be accidental copies, but repeated identifiers can also represent legitimate events if the assumed key is wrong. Keep a note of how many rows were removed and why, so the analysis remains reproducible.

5. Validate allowed values and plausible ranges

Domain rules often catch problems that generic statistics cannot. An age of 240, a negative quantity of shipped items, or a rating outside the documented scale deserves investigation. The correct boundary depends on the source and business context.

# Example rules: adapt these to your dataset
if "age" in df.columns:
    invalid_age = df["age"].notna() & ~df["age"].between(0, 110)
    print("Rows with implausible age:", invalid_age.sum())

if "rating" in df.columns:
    invalid_rating = df["rating"].notna() & ~df["rating"].between(1, 5)
    print("Rows outside rating scale:", invalid_rating.sum())

For categories, compare observed values with an approved set where one exists. For dates, check impossible sequences such as a delivery date earlier than an order date. Treat these checks as flags for review—not automatic proof that a record must be deleted.

6. Look for inconsistent categories and units

Category variations can split one real group into several misleading groups. Inspect frequent values and whitespace before normalizing them.

for col in df.select_dtypes(include="object").columns:
    print("\n", col)
    print(df[col].astype("string").str.strip().value_counts().head(10))

Standardize only when the values clearly mean the same thing. Also check units: mixing centimetres and inches, or rupees and thousands of rupees, can create plausible-looking but incorrect numbers. Record any conversion rule alongside the project code.

7. Review outliers without deleting them automatically

Outliers may be data-entry errors, rare but valid events, or the most important cases in the dataset. Use summary statistics, box plots, and domain context to investigate them. If you use an IQR rule as a screening method, label the flagged rows and inspect them rather than treating the rule as a universal deletion policy.

col = "monthly_spend"  # replace with a numeric column
q1 = df[col].quantile(0.25)
q3 = df[col].quantile(0.75)
iqr = q3 - q1

flagged = df[df[col].notna() & (
    (df[col] < q1 - 1.5 * iqr) |
    (df[col] > q3 + 1.5 * iqr)
)]
print("Potential outliers:", len(flagged))

8. Prevent target leakage before training

Dataset quality includes checking whether a feature would actually be available at prediction time. A cancellation reason recorded after cancellation, a final invoice total, or a status updated after the outcome may reveal the answer instead of helping the model predict it. Such a feature can create impressive offline scores and poor real-world performance.

For each feature, ask: Would this value exist at the exact moment the prediction is supposed to be made? If not, exclude it or redesign the problem. Use a split that matches the real use case—chronological splits for future forecasting and group-aware splits when related records could otherwise appear in both training and test data.

9. Make validation repeatable with a small report

Keep the checks in a notebook or script and produce a concise report each time the data changes. At minimum, include row and column counts, missing-value percentages, duplicate counts, failed business rules, category anomalies, and any decisions taken. If the data is updated regularly, the report makes changes easier to notice.

10. Turn the checks into a portfolio habit

A strong data science project README should explain the dataset source, what one row means, the main quality issues discovered, the cleaning decisions, and how those decisions may affect the results. Include the validation code and a small summary table; do not publish private or sensitive raw records just to prove that checks were performed.

During Data Science Training in India, practise this routine on different datasets rather than relying on a single clean tutorial file. It helps connect Python syntax to statistical judgment, reproducibility, and responsible machine learning.

Before you train: a practical checklist

  • ☐ I can explain the unit of observation and the intended prediction task.
  • ☐ I checked shapes, types, date parsing and unexpected values.
  • ☐ I measured missingness and inspected duplicate candidates.
  • ☐ I tested domain ranges, category consistency and units.
  • ☐ I reviewed outliers instead of deleting them automatically.
  • ☐ I checked feature availability and leakage risk.
  • ☐ I documented cleaning decisions and made the checks repeatable.
  • ☐ I will fit preprocessing steps using training data only.
